# Phase 2 startup repair and replacement

The supplied Output shows a **Client** CorePackages/UIBlox FoundationProvider
warning and a client waiting for `ReplicatedStorage.Riftbound`. The UI warning is
inside Roblox's UI packages, not these five scripts. Neither message identifies
the underlying server failure. There was no Riftbound server traceback in that
log, so the precise cause in that Studio place is **not confirmed**.

## Comparison with the reported working version

Compared the raw files at working Phase 1 commit `8cb80dc` and Phase 2 commit
`d3fb74a`. Both required Config, RealmState and World and called Realm.new **before**
creating the Riftbound folder. A missing/wrong dependency, module syntax/runtime
error or state-construction exception could therefore stop the server while the
client waited forever. A disabled, misplaced, wrong-class or client-context server
Script produces the same client symptom.

Phase 2 introduced duration assertions during Realm.new and new World/config
contracts. Mixed versions or invalid durations can fail during initialization.
Its SceneUpdatesPerSecond/SnapshotSeconds checks and World.build happened **after**
folder creation: those failures can explain a missing map, but do not by themselves
explain the reported missing folder. No syntax failure was found in the committed
five Phase 2 files; that does not establish what source was pasted into Studio.

## What this repair changes

- The server creates Riftbound and its Snapshot/Action/Notice RemoteEvents before
  loading any modules. Three require paths remain the same sibling paths.
- Bounded checks identify absent, duplicate and wrong-class ModuleScripts.
  Export checks reject incomplete/older World and RealmState modules clearly.
- Missing new Config settings receive defaults; invalid explicit settings fail
  with the field name. Persistence must remain false.
- Each startup stage is captured, with the original exception/traceback in SERVER
  Output and `StartupError`. Ready becomes true only after World.build and the
  first World.render succeed. Animation/round-render errors stop that loop and
  publish their error instead of repeatedly failing silently.
- The client shows its loading/error panel before looking for remotes. All startup
  waits have timeouts. It displays the failing stage and original error's first
  line. Full traces stay in server Output/StartupError. A later runtime failure
  shows the error panel and releases the stream camera.

The world, procedural avatar movement, competitions, income, gift effects, demo
events, leaderboards and portrait HUD remain Phase 2. No external requests or
save-service access were added. The optional Node bridge remains separate.

## Exactly what to replace

**Two source files changed:** Realm.server.lua and Realm.client.lua. Replace both
together. Config.lua, RealmState.lua and World.lua are identical to Phase 2 commit
d3fb74a; their complete sources are included so a mixed-version place can be repaired.
If you cannot confirm all three modules already match that Phase 2 version, replace
all five with the supplied sources. Do not combine files or add duplicate scripts.

1. Save a place backup and **Stop Play**. Edits made only to the running session
   are discarded when it stops.
2. In Explorer, verify this exact tree, with extension-free instance names:

   ```text
   ServerScriptService
   ├── Config      ModuleScript — Config.lua
   ├── RealmState  ModuleScript — RealmState.lua
   ├── World       ModuleScript — World.lua
   └── Realm       Script       — Realm.server.lua
   StarterPlayer
   └── StarterPlayerScripts
       └── Realm   LocalScript  — Realm.client.lua
   ```

3. Open each required instance in the **Script Editor**, select all old source and
   paste the **entire matching raw file**. All five full code blocks are also in
   `MANUAL_STUDIO_SETUP.md`. Do not paste Markdown fences or use the Command Bar.
4. Select the server Realm in Properties: it must be a normal Script, enabled,
   with **RunContext = Legacy** (Server also runs on the server; Client does not).
   Select the client Realm: it must be an enabled LocalScript in the folder above.
   Keep exactly one of each. Do not rename a ModuleScript to Realm as a substitute.
5. With Play stopped, remove only any **manually saved/generated test copies** of
   ReplicatedStorage.Riftbound, Workspace.RiftboundRealm or the BindableFunction
   ServerScriptService.RiftboundEvent left from an earlier manual attempt. These
   are runtime objects generated by the server. A saved BootstrapClaimed attribute
   can otherwise look like a second running server; the corrected server warns.
6. Keep HTTP Requests and Studio API Services access disabled. Keep Config's
   PersistenceEnabled false. No Node process, plugin or publication is required.
7. Open Output and press **Play**, not Run. The SERVER Output success message is:

   ```text
   [Riftbound] Ready: modules loaded, world built, first snapshot rendered.
   ```

8. The map/HUD should appear, followed by demo arrivals and automatic rounds. Run
   `docs/PLAYTEST.md` to verify all three rounds and Phase 2 visual behavior.

If startup still fails, inspect **the Server view** of Output and the on-screen
stage/error. During Play, select ReplicatedStorage → Riftbound and inspect its
Ready, StartupState, StartupStage and StartupError attributes. A missing folder
after 10 seconds with this corrected server means the bootstrap did not execute
far enough to create it: check the server's source, syntax, enabled state, class,
parent and RunContext first. Do not create a dummy folder to silence the client.
For a failed stage, use the original error and script/line in the server traceback.
The FoundationProvider warning is not a replacement for that diagnostic.
